# External manual verification run template

**Template status: NOT RUN.** This document defines user-run manual checks that CI and the repository's non-AI benchmarks cannot perform. It contains no manual results. Copy this file to a separately dated run report after performing checks; do not edit this template to make it appear that a run occurred.

## Safety and evidence rules

- Use only synthetic exam/question records, invented prompts, and a synthetic image created for testing. Do not use real study material or personal images.
- Never request, copy, log, screenshot, upload, or record passwords, OAuth/account/API tokens, API keys, personal account identifiers, real study data, or secrets. If an unexpected secret appears in a screenshot/log, discard that evidence and do not attach it.
- A tester signs in directly on their own computer using the app and their own eligible account. This template must not be used to collect account access or tokens.
- Run all checks on a physical device separate from the development device and all CI runners. A VM/container on the development device does not satisfy this requirement. Record the test device OS/version and whether it is physically separate; if the answer is `NO`, mark affected rows `BLOCKED` without treating them as consumer-device verification.
- For flows that display a consent screen, read the destination, payload summary, transport warnings, and consent prompt before sending. Do not proceed if the destination is unexpected or the user does not trust its operator. A configured OpenAI-compatible URL can be remote. The question-analysis **Review with AI** flow shows a sanitized hostname/effective port, local/remote class, scheme, model, text/image payload fields, and authentication-value category before every send. Its preview and cancel request use only the local API; provider traffic starts only after affirmative approval. Study Agent consent remains a separate flow and excludes saved question images. Record only non-sensitive outcomes; never record credentials, key values, or a full URL containing secrets.
- Use a separate disposable OS user/profile and test data where practical. Remove synthetic records and test profiles after verification where doing so is safe. Preserve normal user data.
- Do not run these checks in CI or benchmark jobs. Real ChatGPT, local model, and remote endpoint execution stays outside automated tests and benchmarks. CI/build/package results and benchmark outputs are separate evidence and must not be copied into these manual result fields.
- Every row begins `NOT RUN`. After an actual attempt, select exactly one outcome: `PASS`, `FAIL`, or `BLOCKED`. `BLOCKED` means the check could not be completed for a recorded non-sensitive reason; it is not a pass. Leave all rows `NOT RUN` if no human run occurred.
- Record the tested OS/version, hardware class if relevant, package type, app version, and exact `ARETE-###` release tag or `unreleased` build. Do not infer the app tag from a docs-only tag or CI run.
